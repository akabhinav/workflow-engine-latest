# Landmine Register — Tranto

The dangerous truths an engineer inheriting Tranto must know before touching the runtime. Ranked by
severity. **Context that reframes all of these:** Tranto is an honest, well-tested *proof-of-core*
rebuild. Its own `STATUS.md` says the distributed layer needs "production-hardening." The landmines
below are almost entirely **"the standalone engine is correct; the distributed engine shares only
queues + flow/execution repos, so anything relying on in-JVM state silently breaks across nodes,"**
plus a few smaller sharp edges. Every item is evidence-backed and corroborated against the project's
own docs where possible.

> **Update (2026-07-11) — distributed hardening complete:** landmines **#1, #2, #3, #4, #7 are now
> RESOLVED** in code (see the ✅ markers below). The JDBC queue is at-least-once (lease +
> ack-after-success + redelivery + purge); a cluster-wide `JdbcLock` serialises each execution across
> executor nodes; the scheduler fires cron once via a leader lease; and **#3 is closed** — concurrency
> admission (`JdbcConcurrencyStore`), KV (`JdbcKVStore`), storage (`JdbcStorage`), and subflow-join
> (parent ref persisted on the child execution) are all cluster-wide now. **Distributed mode is safe to
> scale executor nodes.** Proven by `JdbcQueueRedeliveryTest`, `JdbcLockTest`, `DistributedHardeningTest`.

| # | Severity | Type | Description | Where | Why it's dangerous | Evidence | Suggested action |
|---|----------|------|-------------|-------|--------------------|----------|------------------|
| 1 | ✅ **RESOLVED** | Silent data-loss path | The JDBC queue marks a message `consumed=TRUE` **before** its consumer runs, with **no visibility timeout and no redelivery**. A node that claims a `worker-task`/`execution`/`worker-result` and then crashes loses that message permanently — the execution hangs forever. | `JdbcQueue.claimBatch` — `UPDATE … SET consumed=TRUE` at `JdbcQueue.java:124-131`, dispatch after | At-least-once is the stated correctness premise (`Executor.java:20-27`), but the JDBC transport is **at-most-once after claim**. Under real node churn, executions silently stall with no error and no retry. | code + `STATUS.md` line 174 ("SKIP LOCKED not done"), line 178 ("recovery" not done) | Move claim to *after* successful processing, or add a visibility-timeout/lease + reclaim of stale in-flight rows before production. |
| 2 | ✅ **RESOLVED** | Cross-node race / lost update | In distributed mode, multiple **executor** nodes can process the same execution concurrently. The correctness lock is a **per-JVM `ConcurrentHashMap<String,ReentrantLock>`** — it does not span nodes. Two executors reading→mutating→`MERGE`-writing the same `executions.data` JSON blob race with last-writer-wins. | `Executor.locks` at `Executor.java:37`; `JdbcExecutionRepository.save` = `MERGE` (whole-doc overwrite) | The single invariant the whole design rests on ("per-execution lock serialises processing") holds only in one JVM. Run two `--role executor` nodes and task-run updates can be silently lost/overwritten. | `Executor.java:26-27` (lock is "the correctness primitive"); `DistributedEngine` reuses the same `Executor` | Run **at most one executor node** until a shared lock exists (DB row lock / advisory lock / single-executor election), OR document executor as singleton. |
| 3 | ✅ **RESOLVED** | Per-node state masquerading as shared | Concurrency admission, KV store, and object storage are **per-instance in-memory / local-FS even in `DistributedEngine`**. So per-flow concurrency limits, `kv.Get/Set`, `LocalStorage`, and the `subflowParents` join map are **not cluster-wide**. | `Executor.runningByFlow/queuedByFlow/slotByExecution` (in-mem maps); `RunContextFactory` `MemoryKVStore`+`LocalStorage`; `Executor.subflowParents:40` | A "limit: 1" flow runs N times across N nodes; a value `Set` on node A is invisible to node B; a **subflow spawned on node A cannot be joined by node B** (parent hangs). Looks distributed, behaves per-node. | `DistributedEngine.java:33-36` Javadoc explicitly admits this; `STATUS.md` lines 172, 179 | Treat distributed mode as *executor-singleton + worker-fanout only* today; move admission/KV/storage/subflow-join to shared JDBC state before scaling executors. |
| 4 | ✅ **RESOLVED** | Duplicate work | The scheduler has **no locking or leader election**. Every node started with the scheduler role (incl. `--role all`) fires **every** due cron trigger → duplicate executions per tick across the cluster. | `Scheduler.java` (in-mem `entries`, no coordination); `ServerCommand --role all` default | Cron flows silently double/triple-execute in any multi-node deployment. | `STATUS.md` line 165 ("trigger locking … not done") | Run the scheduler role on exactly one node, or add scheduler leader election / DB-backed trigger locks. |
| 5 | **Med** | Incomplete feature / source-schema contradiction | Flow **revisions are not real**. `Flow.revision` exists and the `flows` table has a `revision` column, but both repos ignore it: memory keeps only the last save per `(tenant\|ns\|id)`, JDBC's PK **excludes** `revision` and `findById` never filters by it. | `MemoryFlowRepository.java:20`; `JdbcFlowRepository.findById:54`; `JdbcDatabase.java:56-63` (PK omits revision) | Re-registering a flow **overwrites history**; in-flight executions pinned to an old `flowRevision` will re-resolve against the new definition (`Executor.process` looks up by ns/id, revision ignored) → an execution can silently change behaviour mid-run on redeploy. | code; `STATUS.md` line 189 ("revisions" not done) | Either enforce single-revision semantics explicitly, or make `revision` part of the key and resolve executions against their pinned revision. |
| 6 | **Med** | Missing error handling on a critical path | `Worker.process` emits exactly one result per task, but if the **result queue emit itself fails**, or an exception escapes outside the guarded `run()` block, no `worker-result` is produced and the execution hangs (no lock timeout, no watchdog). Similarly `Scheduler.tick` swallows all exceptions silently. | `Worker.java:40-73`; `Scheduler.start:93-99` (`catch (Exception ignored)`) | A single dropped result or a persistently-throwing trigger stalls an execution / silently disables a schedule with no signal. | code | Add an execution watchdog / heartbeat + a dead-letter path for undeliverable results; log (not swallow) scheduler tick failures. |
| 7 | ✅ **RESOLVED** | Unbounded growth | `queue_messages` rows are **never deleted** — every message ever sent (work, results, state updates) accumulates forever; the poll query relies on an index but the table grows without bound. | `JdbcQueue` (no DELETE/purge anywhere) | Long-running clusters accumulate millions of dead rows; poll latency and storage degrade. | code; `STATUS.md` line 173 (partitioning not done) | Add a purge/retention job or delete-on-consume for terminal topics. |
| 8 | **Med** | Non-2xx HTTP silently succeeds | `http.Request` treats **any** HTTP status (incl. 4xx/5xx) as success — non-2xx is explicitly not an error. | `plugin-core/.../http/Request.java:29` (documented behavior) | A workflow that calls a failing API sees a "successful" task with a 500 body and proceeds; failures must be asserted manually downstream. | code comment + output shape `HttpOutput(status, body)` | Document clearly; consider an opt-in `failOnStatus`; teach authors to `Assert` on `{{ outputs.x.status }}`. |
| 9 | **Med** | Arbitrary command / SQL / URL execution | `script.Commands`→`Process` runs arbitrary shell (`cmd.exe /c` / `sh -c`); `jdbc.Execute/Query` run arbitrary SQL with credentials in the flow; `http.Request` hits arbitrary URLs. No sandboxing, allow-listing, or secret management. | `Process.java:43-62`; `jdbc/Execute.java`, `Query.java`; `Request.java` | Anyone who can register/run a flow has RCE, arbitrary DB access, and SSRF on the host. Fine for a single-tenant dev tool; dangerous if the REST API is ever exposed multi-tenant (no auth exists — see #10). | code | Before any shared/multi-tenant exposure: add auth, secret store, command/SQL/URL policy. |
| 10 | **Med** | No authentication / tenancy | The REST API has **no auth, CSRF, or tenant enforcement**; `tenantId` is threaded through everything but always null/`""`. | `webserver` controllers (no security config); `STATUS.md` line 183 | The API is fully open; combined with #9, exposing port 8080 = full host compromise. Tenancy columns imply isolation that isn't enforced. | code; `STATUS.md` | Keep bound to localhost/dev only until auth + tenancy are implemented. |
| 11 | **Low** | Dead / partially-wired code that looks live | Several `StateType` values are defined and look load-bearing but are **not emitted by the engine**: `RETRYING`, `BREAKPOINT`, `RESUBMITTED` (and `RESTARTED` only via the `isCreated` predicate). Retries jump FAILED→SUBMITTED without ever setting `RETRYING`. | `StateType.java:16-52` vs `Executor.tryRetry:253-257` (uses SUBMITTED, not RETRYING) | An operator reading the state enum will expect a `RETRYING`/`BREAKPOINT` state that never appears; dashboards keyed on them stay empty. | code | Document which states are aspirational, or wire them (set `RETRYING` during backoff). |
| 12 | **Low** | Divergent duplicate logic | The blocking-run + input-resolve + fail-fast + `onExecutionUpdated` logic is **copy-pasted** between `StandaloneEngine` and `DistributedEngine` and has already diverged: `StandaloneEngine.onExecutionUpdated` updates metrics counters; `DistributedEngine.onExecutionUpdated` does not (no metrics in distributed mode). | `StandaloneEngine.java:184-196` vs `DistributedEngine.java:172-180` | Fixes/features applied to one engine silently miss the other (metrics already lost in distributed mode). | code (side-by-side) | Extract the shared submit/run/lifecycle into one base or collaborator. |
| 13 | **Low** | Truthiness / coercion foot-guns | "Truthy" is inconsistent: `If`/`runIf` accept only `"true"`/`"1"` (case-insensitive); `Assert` requires literal `"true"`. A rendered `"TRUE "`, `"yes"`, or `"2"` is falsy. Loop value parsing strips `[]`/quotes heuristically. | `If.isTruthy:49-55`; `Worker.shouldRun:108-109`; `Assert.java:39-44`; `Loop.java:59-78` | Authors expecting general truthiness get silently-skipped branches / failed asserts; brittle Loop parsing. | code | Document the exact truthiness rules; unify into one helper. |

## Cross-cutting notes

- **The good news first:** the *standalone* engine's correctness story is genuinely solid — immutable
  `Execution`/`TaskRun`, per-execution locking, idempotent delta-apply, a *pure* `ExecutionPlanner`,
  and 31 test classes including in-database showcases. The landmines are overwhelmingly about the
  **distributed** wiring, which the project openly labels as not-yet-hardened.
- **The single mental model to carry (updated 2026-07-11):** the old *"only `queue_messages`, `flows`,
  `executions` are shared; everything else is per-JVM"* no longer holds. Now **also shared**: `locks`
  (per-execution serialisation + scheduler leadership), `kv_store`, `storage_objects`,
  `concurrency_slots`, and the subflow parent-ref (persisted on the child execution). The queue is
  at-least-once. Landmines #1–#4 and #7 are closed; the remaining per-JVM item is **#12 (metrics)**.
- **Lineage leak (harmless but telling):** `StorageInterface` Javadoc still says `kestra://` while
  `LocalStorage` emits `tranto:///` (`StorageInterface.java:14` vs `LocalStorage.java:19`) — confirms
  the Kestra provenance and that some comments predate the rename.
- **No git history** means none of the above can be cross-checked against when/why it was introduced;
  treat the STATUS.md "NOT DONE" list as the authoritative companion to this register.
